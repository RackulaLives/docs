# Rackula Docs Starlight Refit Design

Status: Approved for implementation planning
Date: 2026-07-04

## Context

The current Rackula docs site is already on Astro 7 and Starlight, with MDX content, Pagefind search, Dracula theming, and a Cloudflare Workers static-assets deployment. The issue is not that the stack cannot provide left-side navigation or page outlines. Starlight already supports those patterns. The issue is that the current site feels too stock and loose: navigation is not prominent enough, section labels do not guide users strongly, and the homepage reads more like a card catalogue than a product-docs entry point.

We compared a Starlight refit against a SveltePress migration. The selected direction is to stay on Starlight and redesign the information architecture, navigation treatment, content structure, and theme polish before considering a platform migration.

## Goals

- Make the left sidebar the primary map of the product documentation.
- Replace loose autogenerated-feeling navigation with deliberate, task-oriented sections.
- Keep Rackula's Dracula identity while improving readability, contrast, and scan speed.
- Make the homepage a compact launchpad into common user paths.
- Keep the implementation bounded: prefer Starlight config, frontmatter, CSS, and content edits before component overrides.
- Preserve the current Astro/Starlight deployment model.

## Non-Goals

- Do not migrate to SveltePress, Docusaurus, Nextra, or Mintlify in this pass.
- Do not rebuild Starlight's complete layout system.
- Do not introduce a new design system dependency.
- Do not add an AI assistant, hosted search provider, analytics layer, or CMS.
- Do not rewrite all documentation content unless needed for navigation clarity.

## Platform Decision

Stay on Astro + Starlight for the prototype and implementation plan.

Rationale:

- The existing content and MDX component usage can mostly stay in place.
- Starlight already provides the docs primitives Rackula needs: sidebar, page outline, search, SEO, code rendering, MDX, and built-in content components.
- Astro remains a good fit for Rackula, and Svelte islands can be added later through Astro's Svelte integration if the docs need interactive examples.
- A SveltePress migration is still a valid fallback, but it should be justified by a failed Starlight prototype, not by the current site's visual state.

## Information Architecture

The sidebar should be manually ordered around user intent:

1. Start
   - Quick start
   - First rack walkthrough
   - Interface tour
2. Build layouts
   - Racks
   - Devices
   - Airflow and spacing
   - Import and export
3. Reference
   - Keyboard shortcuts
   - Brand packs
4. Deploy
   - Self-host with Docker

The current "Self-Hosting" section should be renamed to "Deploy" in navigation. The page path can remain under `self-hosting/` unless a redirect plan is added later.

## Navigation Behaviour

The left sidebar is the main site map. It should be visible and useful on desktop, with stronger section headings, clearer active state styling, and a denser but still readable rhythm.

The right "On this page" outline remains the section-level navigation for long articles. It should not compete visually with the left nav; it should act as a local outline.

Search should remain available near the top navigation and should feel like a core workflow, not a tucked-away feature.

Mobile navigation should keep the same IA and avoid hiding important paths behind unclear labels.

## Page Structure

The homepage should become a compact launchpad:

- A short Rackula docs headline and practical value statement.
- A primary quick-start path.
- Three or four task-oriented entry points matching the sidebar sections.
- Links to the live app, GitHub, and deployment docs.
- No large marketing-style hero that pushes documentation paths below the fold.

Standard content pages should use a consistent pattern:

- Short contextual intro.
- Optional "Before you begin" block when prerequisites matter.
- Task-first steps near the top.
- Reference details after the practical path.
- Next-step links at the bottom.

Long pages should be split only when the sidebar benefits. Splitting purely to reduce scroll is not useful if it hides related decisions across pages.

## Visual Direction

Keep the Dracula dark theme, but rebalance the palette so purple is not responsible for every action and emphasis. Use:

- Purple for primary active navigation and brand emphasis.
- Cyan for search, metadata, and wayfinding.
- Green for successful or recommended actions.
- Orange for warnings, tips, and "before you begin" callouts.
- Neutral greys for structure, borders, and secondary text.

The UI should feel like a dense product manual, not a marketing page. Use compact cards, restrained borders, tighter headings, and clear active states. Avoid decorative gradients, oversized splash patterns, and nested card layouts.

Typography should keep JetBrains Mono for headings and Inter for body text, but page headings and compact panels should use sizes appropriate to their container.

## Component Strategy

Use the lightest customisation that achieves the design:

1. Starlight config for sidebar order and labels.
2. Page frontmatter for sidebar labels and ordering where autogeneration remains useful.
3. CSS variables and targeted selectors for navigation, cards, search, tables, and active states.
4. Content edits for homepage and key guide pages.
5. Component overrides only if CSS/config cannot produce the required behaviour.

Likely override candidates:

- Homepage/hero treatment if Starlight's splash template remains too broad.
- Footer or pagination treatment if next-step links need stronger affordance.
- Sidebar-adjacent UI only if Starlight's default markup prevents the intended active-state or grouping treatment.

Avoid overriding Starlight core layout components unless the prototype proves it is necessary.

## Content Changes

Rename and reorganise visible navigation labels:

- "Getting Started" becomes "Start".
- "Guides" becomes "Build layouts".
- "Self-Hosting" becomes "Deploy".
- "Core Concepts" content moves into the user path where practical, with concept pages retained only when they are valuable standalone references.

Update homepage link cards and guide intros to match those section names.

Use Canadian/British spelling throughout, including "colour", "organise", "behaviour", "centre", and "visualise".

## Error Handling And Edge Cases

The primary risk is making Starlight feel custom through brittle selectors. Mitigation: keep selectors scoped, prefer documented Starlight variables, and use component overrides only for stable, intentional boundaries.

The second risk is changing URLs while reorganising labels. Mitigation: prefer label and sidebar changes first; defer path changes unless there is a clear redirect plan.

The third risk is making the sidebar denser but less usable on mobile. Mitigation: verify desktop and mobile navigation in browser before completion.

## Verification

Implementation should be verified with:

- `npm run build`
- Browser review of the homepage, quick start, a long guide page, and the Docker deployment page.
- Desktop and mobile viewport checks.
- Specific checks that:
  - the left sidebar shows Start, Build layouts, Reference, and Deploy;
  - active sidebar state is visible;
  - the right page outline still works on long pages;
  - homepage paths are visible without excessive scrolling;
  - no text overlaps or overflows in nav, cards, buttons, or callouts.

## Rollout

Implement as a prototype-sized pass on the current Starlight site. If the result still feels boxed in by Starlight after visual review, revisit SveltePress with evidence from the prototype instead of migrating speculatively.
